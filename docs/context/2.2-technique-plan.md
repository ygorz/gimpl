# 2.2 Context-management technique plan (port-planner, P_GiveArtifact)

Companion to `docs/context/2.2-pre-session-plan.md`.

## 1. Explicit boundary: Phase 1 (Map) -> Phase 2 (Draft spec)
At this boundary I tell the agent:
- Phase 1 is complete; the caller/field/demo map is the input to Phase 2.
- Phase 2 focuses on writing `docs/port-specs/p_inter-giveartifact.md`.
- Still active: cite file:line, the stay-C fence word for word, 4227 gametics
  for DEMO1, wad sha256 pinned and never modified.
- Changed: "no file edits" is retired; the agent may now write the spec file only.
- Carried forward: the Phase 1 map (callers, `player_t` fields, `MF_COUNTITEM`, demo coverage).

Why here: this is where the governing rule flips from read-only to write. Without
a boundary, the agent may keep acting read-only or treat "may write" as license
to touch files outside `docs/port-specs/`.

## 2. Explicit boundary: the DEMO3 requirement change
Introduced after the agent drafts the verification section. I tell the agent:
- The DEMO1-only verification plan is superseded.
- Active: DEMO1 stays pinned at 4227 gametics; DEMO3 is added at 2582
  gametics, marked **not yet pinned** until Feature 1.
- It must revisit the Phase 1 demo map and the spec's verification section.

Why here: the change lands on work already written, so the old DEMO1-only rule is
sitting in context. Restating it guards against reverting to DEMO1 only, and
against "pinned" wording leaking onto DEMO3.

## 3. Proactive summary: `/summarize-session` after the DEMO3 update is applied
The summary must keep: the current goal, active rules verbatim (including the
fence and both demo numbers), decisions so far, the current spec text,
unresolved questions, and the next action. I check it against the spec file
before continuing and save it to `docs/context/2.2-summary.md`.

Why here: this is the point of most accumulated context, right after a rule
change, which is where a summary is most likely to drop or blur the new rule.

## 4. Handoff: `/write-handoff` at the end
Saved to `docs/context/2.2-handoff.md` as the planner-to-implementer brief for
Feature 2. It carries the final spec state and current rules only.

## 5. Compaction: only if `/context` shows the window getting crowded (about 60%)
Not planned on purpose. If used, I save the spec text to its file first.

## Why a summary over compaction
With a summary I choose what survives and can check it word for word against the
files. In the 2.2 lesson probe, `/compact` kept the rules but distorted exact
artifact text, and exact numbers (4227, 2582) and the fence wording are what
this spec depends on. The tradeoff: a summary costs a turn and my review time,
which compaction would not. The iteration log will record whether this choice
held up.
